# Pure: 기록을 버릴 수 있는 실행 코어

2026-09-22. **자체 실행 계약의 첫 C17 구현. 정확성과 자원 한도를 확인했으며,
독창성·성능 우위·제품 통합은 아직 검증하지 않았다.** 새 문법이나 화면 데모는 없다.

후속: [기존 작성물의 표시 계산에 실행 계약을 이식](../../docs/research/009-bounded-display-integration.md)했다.
아래 정수 모델의 결과와 별도로, Zig/Wasm의 소수점·상태 변경 의미를 보존해 검증했다.

## 우리가 확인한 질문

> 재사용을 위한 값과 변경 기록을 모두 버릴 수 있게 하면서, 잘못된 결과의
> 재사용을 막고 한 요청이 사용할 작업량까지 제한할 수 있는가?

기억이 부족할 때 정확도를 낮추는 대신 재계산한다. 재계산도 지정한 작업량을
넘으면 결과를 발행하지 않고 `PF_WORK_LIMIT`를 반환한다. 필수 입력·프로그램은
보존한다. 이 계약을 만족하면 재사용 기록을 필수 상태에서 분리하는 구현을
계속 검토할 수 있다. 작은 모델에서도 오래된 값이 발행되거나 한도를 넘으면
이 설계를 폐기·수정하는 것이 이번 작업의 중단 기준이었다.

## 선행기술과 우리 구현의 경계

필요한 출력만 계산하는 것은 이미 [Adapton](https://matthewhammer.org/adapton/)의
연구 대상이다. [Salsa의 튜닝 문서](https://salsa-rs.github.io/salsa/tuning.html)는
LRU가 계산 결과를 제거하며, 질의 키·의존성 메타데이터는 그 제거 대상이 아니라고
설명한다. 이것이 Salsa 전체에 다른 메모리 회수 기능이 없다는 뜻은 아니다.

우리의 이번 구현 선택은 **값·입력 의존성 요약을 담은 캐시와 변경 기록을 모두
고정 크기로 제한하고, 남은 증거로 재사용을 정당화할 수 없으면 버리는 것**이다.
새 이름을 붙인 증분 계산을 발명이라고 주장하지 않는다. 증분 계산, 변경 일지,
보수적인 무효화의 기존 아이디어를 이용한 자체 코어이며, 이 조합의 신규성이나
기존 시스템 대비 개선은 입증하지 않았다. 소수 자료의 확인은 중복 검토의
출발점이며 포괄적인 선행연구 검토가 아니다. 위 자료는 2026-09-22 확인했다.

## 실행 규칙

- 프로그램은 최대 64개 노드의 DAG, 입력은 32개의 `uint64_t`다. 덧셈·곱셈은
  2^64 모듈러 연산이다. 상수·입력·덧셈·곱셈·XOR·조건 선택을 지원한다.
- 조건 선택은 선택한 가지와 조건만 읽는다. 각 결과에 실제 읽은 입력의
  32비트 요약을 합성한다. 자식의 캐시를 써도 그 의존성을 부모에 전한다.
- 캐시는 결과·입력 요약·확인한 revision을 함께 보관한다. 캐시 교체 시
  이 세 가지를 함께 버리며, 별도의 질의별 키 테이블이나 역방향 간선을 남기지 않는다.
- 변경 일지는 고정 길이의 순환 배열이다. 기록이 덮어써지거나 삭제되면
  `history_floor`를 올린다. 그보다 오래된 캐시는 재사용할 근거가 없으므로 재계산한다.
- 기록이 충분하면 캐시의 입력 요약과 이후 변경이 겹치지 않을 때만 재사용한다.
  같은 값의 입력 쓰기는 revision을 올리지 않는다.
- 프로그램 교체는 전체 정의를 검증한 뒤 적용하며 입력을 보존하고 재사용 기록은
  폐기한다. 잘못된 교체는 기존 프로그램·입력·기록을 유지한다.
- revision 오버플로 때는 이전 기록을 폐기한다. 입력 변경·조회·기록 삭제는
  한 스레드에서 순서대로 호출한다. 동시 호출·외부 I/O·이벤트 재실행은 지원하지 않는다.

정확성의 핵심은 다음이다. 기록이 완전한 구간에서 이전 실행이 읽었던 입력이
하나도 변하지 않았다면, 순수하고 결정적인 계산은 같은 분기와 결과를 갖는다.
조건의 의존성도 포함해야 이 논리가 성립한다. 기록이 불완전하면 재사용하지 않는다.
테스트는 이 논증의 구현 오류를 찾는 수단이며 일반적인 형식 증명은 아니다.

## 한도의 의미와 비용

`pf_eval`의 작업 한도에는 실행 단계·캐시 검사·변경 기록 검사가 포함된다.
성공할 때만 호출자의 출력에 값을 쓴다. 중단된 조회에서 이미 완성한 중간 캐시는
남을 수 있지만 입력을 바꾸거나 부분 결과를 발행하지 않는다. 이 한도는 CPU 명령
수나 실제 응답 시간 보장이 아니다. 재시도는 처음부터 시작하며 완료를 보장하지 않는다.

현재 Linux AArch64/GCC 14.2.0에서 `sizeof(PfCore)`는 **3,696바이트**다.

| 고정 영역 | 바이트 |
|---|---:|
| 프로그램 64개 노드 | 1,536 |
| 입력 32개 | 256 |
| 결과·의존성·revision 캐시 8개 | 192 |
| 변경 기록 8개 | 128 |
| 비재귀 평가 스택 64칸 | 1,536 |
| 개수·revision·정책 위치·작업 카운터 | 48 |

코어는 힙 할당을 하지 않는다. 호출자가 제공하는 `PfCore`에 위 영역이 모두 들어간다.
논리적 캐시·기록 용량을 0~8로 조절해도 예약된 3,696바이트는 줄지 않는다.
메모리 압력에 맞춰 실제 저장 공간을 반납하는 할당기는 이번 구현에 없다.
노드 번호가 자식으로 내려갈 때 반드시 작아지므로 평가 스택은 노드 수를 넘지 않는다.

이 수치는 전체 실행 RAM이 아니다. 실행 코드·C 호출 스택·호스트·출력과 로드할
프로그램을 담은 호출자 버퍼는 별도다. GCC의 이 빌드에서 `pf_eval` 호출 프레임
추정은 64바이트였다. 이는 전체 프로세스 스택 측정이나 다른 타깃의 보장이 아니다.
API는 초기화된 코어를 요구하고, 코어 필드의 외부 변경과 입력·출력 인수의 코어 내부
별칭을 허용하지 않는다. `pf_load`에 넘긴 노드 배열도 코어와 겹치면 안 된다.

## 확인한 것과 채택 보류 이유

[검증 기록](verification.json)의 일반 빌드와 ASan·UBSan 빌드가 각각 다음을 확인했다.

- 성공 조회 **116,143개**가 독립적인 순방향 전체 계산과 일치했다.
- 작업량 중단 **16,425회**에서 부분 출력을 발행하지 않았다.
- 각 동작 뒤 결과를 조회하는 조건에서, 여섯 동작의 길이 5 이하 모든 순서와
  아홉 캐시·기록 용량 조합을 확인했다. 동작은 두 입력 변경, 값 삭제,
  기록 삭제, 둘 다 삭제, 한도 0 조회다.
- 고정 seed의 32,000개 추가 동작에서 분기·입력·프로그램 교체·작업 한도를 섞었다.
- 기록 덮어쓰기, 미선택 가지 변경, 31번 입력 비트, revision 오버플로,
  잘못된 정의 거절, 최장 평가 스택을 별도로 확인했다.

역시 중요한 결과는 **캐시가 없으면 작은 DAG도 재계산량이 지수적으로 커질 수
있다**는 것이다. 그런 사례에서는 한도 내 거절을 확인했다. 따라서 ‘항상 적은
메모리와 빠른 응답으로 완료’한다는 가설은 이 계약이 보장하지 않는다.

이번으로 기본 계약 확인을 닫는다. 합성 조건을 늘리는 벤치마크는 만들지 않는다.
제품 채택은 실제 Pure 작업에서 작은 캐시의 반복 중단과 기록 검사 비용이
허용되는지로 판단해야 한다. 현재 작업물의 32개 상태 제한과는 맞지만 큰 문서나
서버의 임의 개수 입력에 적용할 표현은 없다. 메모리 반납·float 오류·상태 전이·
입출력의 의미도 기존 workbench와 통합되지 않았다. 기존 코어를 교체하지 않았다.

## 재실행

```sh
python3 prototypes/forgetful-core/check.py --output /tmp/pure-forgetful-verification.json
```

C17 컴파일러, Python 3, ASan·UBSan이 필요하다. 외부 의존성을 내려받지 않는다.
출력 파일은 새 경로만 허용하며 소스 해시·컴파일러·플래그·호스트를 기록한다.
이 명령은 성능 비교를 실행하지 않는다. macOS 성능은 측정하지 않았다.
